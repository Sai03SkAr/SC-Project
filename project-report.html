Soft Computing · Project Report

Phishing Website Detection using Multi-Objective Feature Selection

Finding the fewest, fastest checks needed to catch a scam website

Algorithm: SPEA2 Dataset: Vrbančič Phishing Dataset Status: Complete
Objectives
  1. To minimise the time required to detect phishing website
  2. To maximize recall value

A third quantity, the false-alarm rate, is optimised alongside these two. It is not a goal in its own right but is required to make objective 2 well-posed — see Section 4.

1. Introduction

A phishing website is a fake site built to look like a real one — a bank, a college portal, a payment page — so that a visitor types in their password or card details and hands them to an attacker.

Software that inspects a link and judges whether it is genuine faces a constraint ordinary classification problems do not: it must decide before the user acts. A detector taking two seconds is useless, because the password has already been typed. So it must be both accurate and fast, and these pull against each other, since every extra check adds a little accuracy and a little delay. This project studies that trade-off directly: we build a phishing detector, then use a soft-computing optimisation algorithm to find which of its 111 checks are actually worth performing.

Why this split is the heart of the project

The 15 lookup features cost over a hundred thousand times more than the 96 text features. So a detector's speed is decided almost entirely by how many network lookups it needs, not by how many features it uses. If our optimisation can discard the lookup features, the detector becomes fast enough to run inside a web browser — which is exactly what Objective 1 asks for.

2.2 Why this dataset was chosen

It is large enough (58,645 sites), peer-reviewed and citable, free, and needs no page download — so detection can happen before the page loads. Most importantly:

Key justification — expect a question here

An older 30-feature phishing dataset (UCI) is the field's traditional benchmark, and we deliberately did not use it as our primary data. With 30 features there are about 1 billion possible combinations, which simpler search methods handle adequately — leaving us unable to justify an advanced optimisation algorithm at all.

With 111 features there are 2111 ≈ 2.6 × 1033 combinations. No computer can test them all, and no simple method searches that space well. This is what makes an intelligent search algorithm genuinely necessary rather than decorative — which is the point of a soft computing project.

3. Aim

The research question

Out of 111 possible checks, what is the smallest and fastest set that still reliably catches phishing websites — and what exactly does speed cost us in accuracy?

The classifier is the instrument, not the subject. We are not inventing a better classification model; we use a standard one (Random Forest) and hold it fixed. What we study is which inputs it needs. Nor are we looking for one answer: because speed and accuracy conflict, there is no single best configuration. We produce the full set of best possible trade-offs, so a deployment can pick the point that suits it.

Two questions to be ready for

Why is f₃ needed if it is not one of our stated objectives? Without it the optimiser finds a trivial cheat: label every website as phishing. Recall then reaches 100%, Objective 2 scores perfectly, and the detector is useless. f₃ closes that loophole — it is what makes maximising recall a meaningful goal rather than a degenerate one.

Why not simply count features for f₁? Counting would rank a 40-feature URL-only subset (0.01 ms) as worse than a 5-feature subset needing a WHOIS query (200 ms) — when the first is about 20,000 times faster. Because features share lookups, cost must be measured by the lookups required, not the feature count.

4.1 Why the objectives conflict

Fewer features means faster detection but less information to judge on. Catching more phishing means flagging more sites, which blocks more real ones. No single configuration is best on all three — improving one always costs something on another. The correct output is therefore not one answer but a set of best-possible compromises.

5. Algorithm — SPEA2

5.1 Why an ordinary optimisation algorithm will not do

The obvious approach combines the objectives into one score using weights — score = w₁·(time) + w₂·(missed) + w₃·(false alarms). This is called scalarisation, and we rejected it for three reasons:

  1. The weights would be arbitrary. There is no principled way to decide speed is worth 0.6 and recall 0.3; the answer would be driven by our guess.
  2. It returns only one answer — one point on the trade-off curve. Changing priorities means running everything again.
  3. It cannot reach some solutions at all. A weighted sum only finds solutions on outward-curving parts of the trade-off surface; those in an inward-curving region are unreachable for any weights whatsoever. This is a mathematical property of the method, not something better tuning can fix.

5.2 What SPEA2 is and how it works

SPEA2 — Strength Pareto Evolutionary Algorithm 2 (Zitzler, Laumanns and Thiele, 2001) is a multi-objective evolutionary algorithm. Evolutionary means it works like natural selection: it holds a population of candidate answers, keeps the better ones, combines and mutates them into a new generation, and repeats. Multi-objective means it optimises several goals at once without merging them into a single score.

Each candidate is a list of 111 yes/no decisions — for each feature, keep it or drop it. To judge a candidate we train the classifier using only its selected features and measure the objectives.

  • Dominance. Candidate A dominates B if A is at least as good on all three objectives and strictly better on at least one. Dominated candidates are discarded.
  • Strength. Each candidate is given a strength value — the number of others it dominates.
  • Raw fitness. A candidate's score is the sum of the strengths of everything that dominates it. Zero means nothing dominates it — it is one of the best found.
  • Density. Many candidates score zero, so ties break by how crowded each one's neighbourhood is. Sparse regions are preferred, spreading results evenly instead of clustering.
  • Archive. A fixed-size store holds the best candidates found so far. When it overflows, the most crowded entries are removed, keeping the spread wide.

The output is a Pareto front — the set of candidates that cannot be improved on one objective without being made worse on another. This set of best possible trade-offs is the project's main result.

5.3 Why SPEA2 rather than the alternatives

  1. It handles duplicate solutions consistently, which our data produces constantly. Our dataset counts the same characters across five sections of the URL, so features are heavily repetitive and many different selections give identical results. SPEA2 gives identical candidates identical scores; NSGA-II can give them different scores. Published research identifies duplicate solutions as a specific cause of poor NSGA-II performance in feature selection.
  2. Its usual disadvantage does not apply to us. SPEA2 is computationally heavier than NSGA-II, but here each candidate requires training a classifier (a few hundred milliseconds) while the algorithm's own bookkeeping takes microseconds — so the difference is invisible.
  3. Recent research favours it. A 2025 IJCAI paper, "Proven Approximation Guarantees in Multi-Objective Optimization: SPEA2 Beats NSGA-II", demonstrates stronger theoretical guarantees for SPEA2.

Rejected alternatives: single-objective PSO and GA handle one objective only; NSGA-III is built for four or more; MOEA/D uses weight vectors, close to the scalarisation we rejected. NSGA-II we still run, as our comparison method, since it is the field's standard reference point.

6. Methodology

  • Load and audit. Verify 58,645 × 112. Investigate the −1 values in the lookup columns — these mark failed lookups, not real measurements.
  • Split the data. 80% training, 20% testing, stratified. The test set is then sealed.
  • Build the cost model. Assign every feature to its lookup type; implement the cost calculation.
  • Establish the baseline. Train on all 111 features, record all objectives. Every later result is compared against this.
  • Run SPEA2. Population 100, 50 generations, repeated with 5 random seeds.
  • Run comparisons. NSGA-II and a weighted-sum PSO under identical conditions, to show what SPEA2 gained us.
  • Analyse the front. Which features survive? How many lookup features were dropped?
  • Final validation. Evaluate the chosen solutions once on the sealed test set.

6.1 How one candidate is scored

if no features selected → return worst possible on all objectives f₁ = detection cost (from the selection; no training needed) train classifier on the selected features f₂ = FN / (FN + TP) (from the confusion matrix) f₃ = FP / (FP + TN) (from the same confusion matrix)

Objective f₁ needs no model training at all, and f₂ and f₃ both come from a single confusion matrix. So evaluating three objectives costs exactly the same as evaluating one — optimising for all of them is computationally free here.

6.2 Preventing data leakage

The key methodological safeguard

Feature selection is a decision learned from data, so it must never see the test set. If we selected features using all the data and only afterwards split it, our results would be invalid. Our order is: split first, select features using only the training data, and evaluate on the test set exactly once at the end.

6.3 How results are measured, and tools

Because multi-objective algorithms return a set of answers, comparing them by accuracy is meaningless. The standard measure is hypervolume — how much of the objective space a Pareto front covers; larger is better. We also report all objectives for each selected solution, with recall, precision and the confusion matrix.

Tools: Python 3 · pymoo (SPEA2, NSGA-II, hypervolume) · scikit-learn (Random Forest, metrics, splitting) · pandas, numpy, matplotlib. All of it runs on an ordinary laptop or in Google Colab. No hardware, no web crawling and no paid services are required.

8. Conclusion

SPEA2 cut the detector from 111 features to 37 and detection cost from 1,320 ms to 490 ms (−63%) while matching the full-feature baseline on unseen data (recall 96.52% against 96.39%; false alarms 4.89% against 5.04%). Both objectives are met.

  • Best algorithm. NSGA-II was the more reliable search — higher and far more consistent hypervolume (1.186 ± 0.008 against 1.155 ± 0.067) — while SPEA2 produced the single best detector on the test set. Both beat weighted-sum PSO (one point per run) and the filter method (85.90% recall).
  • False alarms. A 2% false-alarm rate is reachable, but only at about 90% recall — and the full 111-feature model hits the same limit, so this is a property of URL-based features, not of feature selection. A 57.6% cut-off gives 95.14% recall at 3.95% false alarms.
  • Speed and robustness. With no network lookups (0.01 ms) recall falls to about 90%. Scaling all network latencies ÷3 or ×3 kept the best recall at 95.6–95.8%.

Limitations: one dataset; subsets tuned for a Random Forest; and failed DNS lookups showed an unexpected link to legitimate sites, worth checking on a second dataset.
