Section 1

What we're building

A model that looks at a web address and decides whether it's a scam.

It never opens the page. It only measures things about the URL — how many dots and hyphens it contains, how long the domain is, whether the domain is disguised as an IP address, how many days until the domain expires, whether Google has indexed it. The dataset has already converted all of that into 111 numeric features, so there's no crawling or scraping to do.

Then comes the part the course actually grades. 111 features is far more than necessary, and every feature costs time to compute. So we use a swarm optimization algorithm to search for the smallest set of features that still catches phishing just as well.

The finding is the trade-off: we cut roughly 75% of the features and accuracy barely moved. That's the project.

Every square is one feature. The 96 blue ones are computed instantly from the URL text. The 15 gold ones need network calls — DNS, WHOIS, Google index — and are the slow, expensive ones. If PSO discards most of the gold squares, the reduced model needs no network at all. That would be our headline result.

Three things to know before loading the CSV

1. The target column is named phishing, and the encoding is 0 = legitimate, 1 = phishing. Don't assume — it catches people out.

2. There is no index column. All 112 columns are real: 111 features + the target.

3. If you also use the UCI dataset, note its Kaggle version adds an index column — drop it before training. If the rows are sorted by class, the row number becomes a perfect predictor and your accuracy will be fake.

Section 3

The three objectives

Each one is measurable, so we can point at a number and say "achieved".

1

Build a baseline classifier using all 111 features

Establish how well the problem can be solved before any reduction. This is the control group — without it nothing later means anything.

Measured by: accuracy, precision, recall, F1, ROC-AUC on a held-out test set.

2

Find the minimal optimal feature subset using Binary PSO

Search for the smallest group of features that still classifies well. This is the soft-computing core of the project.

Measured by: features selected, % reduction, and which ones survived.

3

Prove the reduced model is faster without being worse

Compare full vs. reduced on accuracy and speed, and benchmark PSO against a Genetic Algorithm, PCA, and a filter method.

Measured by: accuracy delta, training time, prediction latency per URL in milliseconds.

Why objective 3 is the strongest card

Phishing detection has to run before the user types their password. A detector that takes 300ms is useless. So "we cut features by 77% and prediction time by more than half, losing 0.4% accuracy" isn't a nice-to-have — it's the difference between a deployable system and a lab toy.

Section 4

The method: Binary PSO

PSO is modelled on a flock of birds searching for food. Each bird remembers the best spot it personally found, and knows the best spot any bird found. It moves based on both. Over time the flock converges.

For feature selection you use the binary version:

  • Each particle is a list of 111 ones and zeros — 1 = keep this feature, 0 = drop it.
  • To score a particle, train a classifier using only its selected features and see how well it does.
  • Particles drift toward combinations that score well, flipping bits as they go.
  • After N iterations, the best particle found is the answer.

Why a swarm algorithm is genuinely necessary here

With 111 features, the number of possible subsets is 2111 ≈ 2.6 × 1033. You cannot test them all, and you can't greedily search that space well either. Accepting a very good answer instead of a provably perfect one, because perfect is computationally out of reach — that is the definition of soft computing. This one sentence justifies the entire method.

The fitness function

This single equation is what makes the swarm prefer small and accurate over just accurate.

fitness = α × (1 − accuracy)  +  β × (features_kept / 111) Lower is better. Use α = 0.9, β = 0.1. Without the second term PSO keeps all 111 features forever, because extra features never hurt training accuracy — that term is the entire reason reduction happens. Tuning α and β and plotting the trade-off is an easy bonus section.

Why PSO rather than the alternatives

We need to justify this choice in the report. The honest summary: PSO and GA land in similar accuracy ranges, but PSO gets there with fewer parameters and less runtime.

The argument that wins marks

PCA can compress 111 features into 25 numbers, but those are blends — "0.3 × domain length + 0.2 × dot count + …". Nobody can act on that. PSO returns actual named features, so the result is a deployable shortlist: these 25 checks are worth computing, these 86 aren't. Interpretability is a real advantage, not a consolation prize.

Section 5

The runtime problem — and the fix

Worth knowing up front, because it's the one thing that can stall the project. Every PSO fitness evaluation trains a model. At 30 particles × 50 iterations that's 1,500 trainings. Done naively on 58,000 rows, one run takes hours — and we need 5–10 runs.

The fix (standard practice, and worth writing up):

  • Subsample to ~15,000 rows during the PSO search only
  • Use 3-fold cross-validation, not 5-fold
  • Use a lighter classifier while searching — RandomForestClassifier(n_estimators=50, n_jobs=-1)
  • Then validate the final chosen subset on the full dataset with the full model

That takes a run from hours down to roughly 15–20 minutes. Describing this in the report is itself a contribution — it shows we thought about computational cost, which is squarely on-topic.

Section 7

Mistakes that would sink this

1 · Data leakage — the project killer

If we run PSO on the whole dataset and then split into train and test, the feature selection has already seen the test data. Every reported number becomes meaningless, and an examiner who knows what to look for will spot it.

Correct order: split into train and test first → run PSO with cross-validation inside the training set only → evaluate the chosen subset once on the untouched test set.

from sklearn.model_selection import train_test_split, cross_val_score
from sklearn.ensemble import RandomForestClassifier

X = df.drop(columns=['phishing'])
y = df['phishing']                      # 0 = legitimate, 1 = phishing

# 1. Split FIRST — the test set is now sealed.
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42)

# 2. Fitness uses cross-validation on the TRAINING set only.
def fitness(mask):
    if mask.sum() == 0:          # a particle selecting nothing
        return 1.0               # is the worst possible answer
    cols = X_train.columns[mask.astype(bool)]
    acc  = cross_val_score(
        RandomForestClassifier(n_estimators=50, n_jobs=-1, random_state=42),
        X_train[cols], y_train, cv=3).mean()
    return 0.9 * (1 - acc) + 0.1 * (mask.sum() / len(mask))

# 3. Only after PSO finishes do we touch X_test. Once.
2 · Reporting a single PSO run

PSO is random. One run reports luck. Run 5–10 seeds and report mean ± standard deviation for both accuracy and features selected.

3 · Judging phishing detection by accuracy alone

The two errors aren't equal. A false positive blocks a real site — annoying. A false negative lets someone hand their password to a scammer — serious. Lead with recall on the phishing class and F1, and show the confusion matrix.

4 · A particle that selects zero features

PSO will eventually try an all-zeros particle and crash the classifier on an empty feature set. Guard for it in the fitness function, as in the snippet above.

Section 8

Targets and limitations

What good results look like

Published work on phishing feature selection reports roughly 97% accuracy with around half the features removed. A realistic, defensible outcome for us: 95–97% accuracy keeping 20–30 of the 111 features.

If accuracy comes out at 99.9%, don't celebrate — check for leakage first.

Limitations to state before anyone asks

Volunteering these reads as rigour rather than carelessness:

  • PSO gives no optimality guarantee. We found a good subset, not provably the best one.
  • Results are dataset-specific. The features that work here may not transfer — which is exactly why Phase 07 is worth doing.
  • The data has a fixed collection date. Phishing tactics evolve, so a deployed model would need periodic retraining.
  • URL-only detection has a ceiling. We never look at page content, so a phishing page on a compromised legitimate domain is invisible to this approach.
