Ransomware Detection using Multi-Objective Feature Selection

Can ransomware be caught before it runs, and what does that cost in accuracy?

Algorithm: SPEA2 Datasets: MLRan · RD2024 · UGRansome Status: Complete
Objectives
  1. To minimise the time required to detect ransomware, ideally before it executes
  2. To maximise recall value

As in our phishing study, the false-alarm rate is optimised alongside these two. It keeps objective 2 well-posed. See Section 4.

1. Introduction

Ransomware is malicious software that encrypts a victim's files and demands payment for the key. Hospitals, councils and companies have been shut down for weeks by a single infection.

What makes ransomware different from most malware is that the damage is done the moment it runs. Encryption starts within seconds; by the time a detector has watched the program misbehave, files are already lost. A security tool can judge a program in two ways:

  • STATIC read the file without running it: its header, its embedded text strings. This takes milliseconds, and it happens before the program can do any harm.
  • DYNAMIC run it inside a sandbox (an isolated test machine) and record what it does: files touched, registry keys changed, system calls made. This sees the real behaviour but takes about two minutes per file.

Dynamic features are usually more informative, so speed and accuracy pull against each other. This project applies the method from our phishing study, SPEA2 multi-objective feature selection, to three ransomware datasets. The goal is to find which features are worth collecting, and in particular whether a detector that never runs the file can still catch ransomware reliably.

2.2 Auditing the data before using it

Two problems found, and fixed, before any optimisation

RD2024: the sandbox's own verdict was in the data. The column processes_malicious alone separates ransomware from benign with AUC 0.996. It is not a behaviour but the sandbox's judgement, so using it would let the optimiser copy an existing detector instead of learning one. We removed it together with the four other verdict columns (*_suspicious, files_malicious, network_threats). After this, no single feature exceeds AUC 0.95.

MLRan: a third of the test set also appears in training. 320 of 975 test vectors are exact copies of training vectors. We keep the authors' split, because their 483 features were chosen on it, but every MLRan result is also reported on the 655 unseen test rows, which is the honest measure of generalisation.

2.3 Why these three datasets

  • MLRan and UGRansome were specified for the project. MLRan has the largest search space we know of in a public ransomware set (483 features). UGRansome is small enough to check every possible subset, which gives the true optimum to measure SPEA2 against.
  • RD2024 was our choice for the third. It is recent (2024), openly licensed, covers 12 well-known families (e.g. WannaCry, LockBit, Ryuk, REvil), and has a natural static/dynamic split. Its static features (header fields) are a different kind from MLRan's (text strings), so the method is tested on two independent feature types.
  • Together they span 13, 148 and 483 features. This matters: the 2483 ≈ 10145 subsets of MLRan cannot be searched by anything simple.

3. Aim

The research question

Can ransomware be detected from the file alone, before it runs? If so, from how few features, and what does skipping the sandbox cost in missed ransomware and false alarms?

As before, the classifier is the instrument, not the subject: a Random Forest is held fixed and we study which inputs it needs. The output is not one detector but the full set of best trade-offs, from which a deployment chooses, for example a pre-execution scanner or a full sandbox pipeline.

Why f₃ is essential, and how we saw it happen

Without f₃ the optimiser can label every file as ransomware: recall becomes 100% and the detector is useless. Such "flag everything" detectors really do appear on our Pareto fronts, because nothing beats their recall. Section 6.3 explains how we choose deployment points so that they are never selected.

5. Algorithm — SPEA2

5.1 How it works (recap)

SPEA2 (Zitzler, Laumanns and Thiele, 2001) is a multi-objective evolutionary algorithm. Each candidate is a string of yes/no bits, one per feature (483 bits for MLRan). A population of 100 candidates evolves for 50 generations by two-point crossover and bit-flip mutation; selection works as follows:

  • Dominance. A dominates B if A is no worse on all three objectives and better on at least one.
  • Strength and raw fitness. Each candidate's strength is how many it dominates; its raw fitness is the total strength of those dominating it. Zero means nothing beats it.
  • Density. Ties are broken by distance to the k-th nearest neighbour, so sparse regions of the trade-off are preferred and the front stays spread out.
  • Archive. A fixed-size archive keeps the best candidates; when it overflows, the most crowded are removed.

The output is a Pareto front: detectors that cannot be improved on one objective without becoming worse on another.

5.2 Why SPEA2

  1. Duplicate-heavy fitness. Many different feature subsets give identical scores (MLRan alone has 1,274 duplicate rows). SPEA2 gives identical candidates identical fitness, and its archive truncation handles them consistently.
  2. Its overhead is invisible here. Each evaluation trains a classifier (hundreds of milliseconds); SPEA2's extra bookkeeping costs microseconds.
  3. Weighted sums cannot do the job. They need arbitrary weights, return one point per run, and cannot reach non-convex parts of the front. We run a weighted-sum PSO to show this, and NSGA-II as the standard multi-objective comparison.

5.3 What we had to change for 483 features: the starting population

The standard binary start switches each feature on with probability ½, so every initial candidate holds about 240 of MLRan's 483 features, about 130 of them dynamic. To reach a static-only detector the search must switch off all 260 dynamic features, but bit-flip mutation changes about one bit per child. In practice, a static-only detector is unreachable.

We therefore use a sparse initial population, the usual remedy in large-scale feature selection (cf. SparseEA). Each starting candidate gets its own density, drawn log-uniformly between 1/n (about one feature) and ½. It uses no knowledge of which features are static, and SPEA2, NSGA-II and PSO all receive exactly the same start.

6. Methodology

  • Load and audit. Encode each dataset (hex fields parsed, flag lists one-hot); check balance, duplicates, train/test overlap and single-feature "shortcuts" (Section 2.2).
  • Split. MLRan: the authors' split (3,905 / 975). RD2024 and UGRansome: stratified 80/20. The test set is then sealed.
  • Internal validation split. The training data is split again 75/25. The search trains on the first part and scores on the second; it never sees the test set.
  • Baselines. Random Forest on all features, on static features only, and PCA (95% variance) and a mutual-information filter (top 25).
  • Search. SPEA2 and NSGA-II, population 100, 50 generations, 10 seeds each per dataset; weighted-sum PSO with four weightings.
  • Choose deployment points from the pooled Pareto front, on validation data (6.3).
  • Final validation. Retrain a 200-tree Random Forest on each chosen subset and evaluate once on the sealed test set (MLRan also on its 655 unseen rows).

6.1 How one candidate is scored

if no features selected → worst value on every objective f₁ = 50 ms (+120,000 ms if any dynamic feature) + 10⁻⁵ × n_features train a 30-tree Random Forest on the selected features f₂ = FN / (FN + TP) ┐ from one confusion matrix f₃ = FP / (FP + TN) ┘ on the validation split

6.2 Measuring search quality

Hypervolume (reference point 1.1, 1.1, 1.1 on normalised objectives; maximum 1.331) measures how much of the objective space a front covers. SPEA2 and NSGA-II are compared over 10 seeds with a two-sided Mann–Whitney U test. Wall-clock time was unreliable (the laptop slept during some runs), so search effort is reported as classifier evaluations.

6.3 Choosing a deployment point from the front

For each cost tier we pick the Pareto solution with the lowest balanced error, (FNR + FPR) / 2, on validation data. This gives a pre-execution detector (best static-only) and a full-analysis detector (best overall).

A correction we made, reported openly

Our first rule, copied from the phishing study, was "highest recall in the tier". Here it picked "flag everything" detectors (e.g. 94.6% recall at 64% false alarms), because those are Pareto-optimal on recall. Balanced error needs no hand-picked target and penalises both mistakes equally. The rule uses validation data only; the test set played no part in choosing it.

Tools: Python 3 · pymoo (SPEA2, NSGA-II, hypervolume) · pyswarms (binary PSO) · scikit-learn · scipy · pandas, matplotlib. Everything runs on an ordinary laptop.

7.1 Weighted-sum PSO

PSO ran four weightings of the three objectives from the same sparse start.

  • Weights did not steer it. On RD2024 all four weightings, from "cost first" to "false alarms first", ended at almost the same static-only detector (56–71 features). There was never a sandbox option to choose from, whereas one SPEA2 run returns about 100 trade-offs.
  • It cannot stay sparse. Binary PSO redraws every bit each iteration with probability sigmoid(velocity), which keeps about half the features switched on. On MLRan, where 260 dynamic bits must all be off, the swarm never saw a good static detector again. The "balanced" and "cost" weightings returned a 3-feature detector that flags 95% of benign software. It is cheap, so the weighted score preferred it.
  • Where it worked, it used far more features: 68 against SPEA2's 7 on RD2024, at similar accuracy.

7.2 What the selected features are

RD2024's 7-feature pre-execution detector uses ImageBase, SizeofStackCommit, three properties of the .rdata section (size, address, raw size), and two section flags. These are layout properties of how the file was built: ransomware builders and packers leave a recognisable fingerprint. ImageBase appears in 52% of all SPEA2 Pareto solutions. On MLRan the most-selected static strings include getlogicaldrives (enumerating drives to encrypt), removedirectorya and getexitcodeprocess: plausible ransomware behaviour, visible in the file before it runs.

7.3 An honest caveat: small validation sets over-fit

MLRan's validation split holds only about 500 benign programs, so one false alarm is 0.2%. Choosing the best of 265 Pareto solutions on such a small set rewards luck. SPEA2's full-analysis pick scored 0.2% FPR in validation but 5.1% on the test set. NSGA-II's pick happened to generalise better. On RD2024, with about 2,000 benign validation programs, validation and test agree closely (SPEA2 pre-execution: 1.10% → 1.33%).

7.4 UGRansome: measuring SPEA2 against the true optimum

UGRansome has only 13 features, so we evaluated all 8,191 subsets with the same fitness function (12 minutes) to get the true Pareto front: 34 detectors. The audit found no shortcut feature (the strongest, USD, reaches AUC 0.85), only 63 test rows also present in training, and 208 duplicate rows with conflicting labels: a little label noise.

8. Conclusion

Yes, ransomware can be caught before it runs, at least in RD2024. SPEA2 found a detector that reads 7 PE-header fields in about 50 ms, never executes the file, and reaches 96.12% recall at 1.33% false alarms on unseen test data. Both targets are met. Compared with the full 148-feature sandbox pipeline (98.74% / 0.64%), skipping the sandbox costs 2.6 points of recall and 0.7 points of false alarms, and makes detection about 2,400 times faster.

  • On MLRan, static analysis falls short. The best static-only detector (SPEA2, 73 strings) reaches 93.33% recall at 4.90% FPR; on the 655 genuinely unseen samples, 94.85% at 8.74%. That is 2.4 points of recall better than using all 223 strings, but below target. Reaching ≥ 95% requires the sandbox. NSGA-II's 158-feature detector (98.06% / 3.33%) beat the 483-feature baseline with a third of the features.
  • Best algorithm. SPEA2 and NSGA-II are statistically tied in search quality (Mann–Whitney p = 0.68 MLRan, 1.00 RD2024, 0.15 UGRansome), as in the phishing study. SPEA2 produced the best, and the most compact, pre-execution detector on both datasets; NSGA-II produced the best full-analysis detector on MLRan. Both clearly beat weighted-sum PSO, which returned one point per run and on MLRan collapsed to a useless detector. The filter and PCA either needed the sandbox or all inputs.
  • Against the true optimum (UGRansome), both algorithms recovered all 34 Pareto-optimal detectors once runs were pooled; per run, NSGA-II found the complete front in 7 of 10 runs and SPEA2 in 4 of 10. A 4-feature detector keeps 98.66% recall at 0.91% FPR.
  • Method lesson. At 483 features, the standard random start makes sandbox-free detectors unreachable (0 found in 6 runs). A sparse start, which uses no knowledge of the tiers, found 47–91 per run. Large feature spaces need this.

Limitations: subsets are tuned for a Random Forest. MLRan's small validation set lets the final choice over-fit (7.3). Static features can be evaded by packing, so a pre-execution filter complements a sandbox rather than replacing it. UGRansome's labels are zero-day vs known threats, not ransomware vs benign.
